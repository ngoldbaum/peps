Abstract
========

The buffer protocol keeps exported storage alive, but a read-only
view does not prevent writes through an alias.  This PEP adds an
optional stable-read request: the exporter guarantees that the view's
contents, layout, and backing storage remain unchanged until release.
Multiple stable reads may coexist; conflicting writes and write-capable
exports fail with ``BufferConflictError``.

Python consumers request ``access="stable-read"``; C consumers use
``PyBUF_STABLE_READ``.  CPython checks that the exact exporter type has
declared support.  Each declaring exporter is responsible for
coordinating its supported interfaces.  Native consumers may read a
stable export without copying, even with their thread state detached.


Motivation
==========

:pep:`3118` and the `buffer documentation
<https://docs.python.org/3/c-api/buffer.html>`__ define layout,
lifetime, and writability, but not stable access.  A read-only view
restricts its consumer, but permits writes through aliases:

.. code-block:: python

   data = bytearray(b"abcd")
   reader = memoryview(data).toreadonly()
   writer = memoryview(data)

   # succeeds despite the read-only view
   writer[0] = ord("x")
   assert reader[0] == ord("x")

``bytearray`` prevents resizing while the views exist, but permits
same-size writes through ``writer``.

In a free-threaded build, reads and writes through different views can
race at the C level.  The `memoryview thread-safety guarantees
<https://docs.python.org/3/library/threadsafety.html#thread-safety-memoryview>`__
require external synchronization around mutable backing storage.
GIL-enabled builds face the same problem when native code detaches its
thread state, as ``hashlib`` and compression modules do while reading
input buffers.

Native-language bindings need this guarantee too.  For example, a Rust
binding can expose a buffer as a `shared slice
<https://doc.rust-lang.org/std/slice/fn.from_raw_parts.html#safety>`__,
``&[u8]``, only if its bytes remain unchanged for the slice's lifetime.
A stable export supplies that guarantee without copying.  The binding
remains responsible for the slice's other safety requirements.

This PEP proposes a ``"stable-read"`` request that excludes writable
aliases:

.. code-block:: python

   import io

   stream = io.BytesIO(b"abcd")
   reader = stream.getbuffer(access="stable-read")
   stream.getbuffer()              # raises BufferConflictError

   reader.release()
   writer = stream.getbuffer()     # succeeds
   writer.release()


Overview
========

Stable reads divide responsibility among three parties:

* **CPython** checks the request and the exact type's declared support,
  calls the exporter, and checks the returned fields.
* **The exporter** prevents conflicting access and keeps the exported
  contents, metadata, and storage valid.
* **The consumer** keeps the export alive while using it, checks that
  its native interpretation is valid, and synchronizes transfers
  between threads.

Exporters declare support; consumers need no declaration.  Declaring
support neither makes ordinary acquisitions stable nor guarantees
that every instance or request can succeed.

The stable-read guarantee does not cover interactions between ordinary
accesses.  Consumers manage ownership when sharing an export.  Requests
fail on conflict instead of waiting for the conflict to end.


Specification
=============

What Stable Reads Guarantee
---------------------------

A *stable export* is a ``Py_buffer`` acquired with
``PyBUF_STABLE_READ``.  After ``bf_getbuffer`` succeeds, the exporter
must prevent writes, new write access, and changes that would move,
free, or invalidate the protected storage.

The protection covers:

* every element byte addressable through the view's layout;
* every pointer cell followed when applying ``suboffsets``;
* the contents of ``format``, ``shape``, ``strides``, and
  ``suboffsets``; and
* the exporter-owned storage keeping those bytes and metadata valid at
  their described addresses.

The consumer keeps any metadata stored in its own ``Py_buffer`` valid,
including when it copies the structure (`Keeping the Export Alive`_).
It must not alter the view or its metadata.  If an element is itself a
reference, the guarantee does not extend to the object it refers to.

The consumer may use the view until it begins ``PyBuffer_Release()``;
it must not access the view concurrently with or after that call.
For mutable storage, the exporter continues to exclude conflicts until
its release callback untracks the export (`Ending an Export`_).
Immutable storage needs no such export tracking.

If other processes or I/O operations can change the protected storage
during normal use, the exporter must prevent those changes for the
lifetime of a stable export, or refuse the request.  The guarantee
excludes debugger intervention and arbitrary privileged modification
of process memory.


Requesting a Stable View
------------------------


Python Requests
~~~~~~~~~~~~~~~

The Python interfaces gain a keyword-only parameter:

.. code-block:: python

   memoryview(object, *, access=None)
   BytesIO.getbuffer(*, access=None)

``None`` preserves existing behavior.  The case-sensitive string
``"stable-read"`` requests a read-only stable view.  Other strings
raise ``ValueError``; other types raise ``TypeError``.

For ``access="stable-read"``, ``memoryview`` requests
``PyBUF_FULL_RO | PyBUF_STABLE_READ`` from a non-memoryview argument.
A memoryview argument must already own a stable acquisition, which
the new view shares (`Initially Supported Types`_).

There is no separate support query.  Consumers try to acquire the view
and handle any failure as described in `Errors`_.


C Requests
~~~~~~~~~~

The public C API adds:

.. code-block:: c

   #define PyBUF_STABLE_READ  0x0400
   PyAPI_DATA(PyObject *) PyExc_BufferConflictError;

``inspect.BufferFlags`` gains ``STABLE_READ`` with the same value.
C consumers add the flag to a buffer request and use the existing
acquisition and release functions:

.. code-block:: c

   Py_buffer view;
   int flags = PyBUF_CONTIG_RO | PyBUF_STABLE_READ;
   if (PyObject_GetBuffer(obj, &view, flags) < 0) {
       return -1;
   }

   Py_BEGIN_ALLOW_THREADS
   consume_bytes(view.buf, view.len);
   Py_END_ALLOW_THREADS

   PyBuffer_Release(&view);

A stable request contains ``PyBUF_STABLE_READ`` and exactly one of
these base representations:

* ``PyBUF_SIMPLE``;
* ``PyBUF_ND``;
* ``PyBUF_STRIDES``;
* ``PyBUF_C_CONTIGUOUS``;
* ``PyBUF_F_CONTIGUOUS``;
* ``PyBUF_ANY_CONTIGUOUS``; or
* ``PyBUF_INDIRECT``.

``PyBUF_FORMAT`` may be added except with ``PyBUF_SIMPLE``.  Existing
read-only aliases are accepted by numeric equality; for example,
``PyBUF_CONTIG_RO`` in the example above equals ``PyBUF_ND``.

No other numeric combination is valid.  In particular, a stable request
cannot contain ``PyBUF_WRITABLE``, negative values, unknown bits,
incomplete compound flags, or combined contiguity flags.  These checks
are stricter than some exporters' ordinary request validation.
Requests without ``PyBUF_STABLE_READ`` retain their existing validation
and dispatch behavior.

``PyMemoryView_FromObject()`` remains equivalent to ordinary
``memoryview(object)`` construction.  C code can obtain a stable
memoryview by calling the type with the ``access`` keyword.


.. _Errors:

Handling Errors
~~~~~~~~~~~~~~~

``BufferConflictError`` is a new built-in subclass of ``BufferError``:

=========================  ===========================================
Exception                  Meaning during stable acquisition
=========================  ===========================================
``ValueError``             Invalid numeric request
``TypeError``              Object does not export buffers
Plain ``BufferError``      Undeclared type or unaudited callback
Plain ``BufferError``      Exporter cannot grant this stable request
``BufferConflictError``    Incompatible operation is active now
``SystemError``            Invalid returned ownership or writability
=========================  ===========================================

After `CPython's checks <How CPython Handles a Request_>`_, the exporter
checks whether it can grant the request.  If a check depends on mutable
state that is unsafe to inspect during a conflicting operation, the
exporter reports the conflict first.  Retrying after the conflict ends
may therefore fail for a different reason.  Unrelated failures, such as
``MemoryError``, propagate normally.

A consumer that explicitly accepts weaker semantics may try ordinary
acquisition after an unsupported request.  It must not silently weaken
a ``BufferConflictError`` by falling back to an ordinary view.

The same conflict exception applies to Python-facing operations that
would change storage protected by a stable export.  C interfaces that
cannot raise Python exceptions keep their documented failure
conventions and must leave that storage unchanged.  Cleanup that
cannot fail must preserve active exports; raising an unraisable
exception is not enough.


.. _Ownership and Threads:

Keeping the Export Alive
------------------------

Each successful acquisition needs exactly one release.  A consumer
must keep the export alive for as long as it or anyone sharing that
acquisition uses the view.


Copies and Wrappers
~~~~~~~~~~~~~~~~~~~

A copied ``Py_buffer`` also needs valid metadata.  Some metadata may
live inside the original structure: ``PyBuffer_FillInfo()`` can make
``shape`` point at ``view.len`` and ``strides`` at ``view.itemsize``.
Copying the struct leaves those pointers referring to the original.
The consumer must keep that struct valid, or copy or reconstruct the
metadata elsewhere while retaining the underlying export.  Consumers
must not alter ``view->internal``.

``PyMemoryView_FromBuffer()`` neither takes over nor extends ownership
of an export.  Its caller must keep the underlying export alive until
the wrapper, every dependent view, and every C re-export have finished
using it, then release it.  The wrapper does not itself own a stable
acquisition and cannot grant stable requests.  The same restriction
applies to ``PyMemoryView_FromMemory()``.

An owner that participates in cyclic GC must visit ``view->obj`` and
release the export from ``tp_clear`` or ``tp_dealloc``.


Sharing Between Threads
~~~~~~~~~~~~~~~~~~~~~~~

Plain reads of protected bytes and metadata through already-obtained
pointers require no attached thread state.  Acquisition, release, and
other Python C API calls keep their existing thread-state requirements.

Consumers must synchronize handoffs between threads and ensure that
all accesses through a shared export *happen-before* the call that
releases it, in the C memory model.  The exporter's synchronization
does not provide this ordering among consumers.


Initially Supported Types
-------------------------

This PEP initially adds support to exact ``bytes``, to ``memoryview``
for carrying an existing stable acquisition, and to the private
exporter behind ``BytesIO.getbuffer()``.

``bytearray`` and ``array.array`` are excluded because some of their
mutation or raw-pointer interfaces do not participate in conflict
checks.  ``mmap.mmap`` is excluded because external writers may change
its storage.


``bytes``
~~~~~~~~~

Exact ``bytes`` can provide stable reads without tracking conflicts.
Its construction APIs still need an ownership rule, because
``PyBytes_FromStringAndSize(NULL, size)`` and related APIs let C code
fill in the bytes before sharing them.

Writes through these APIs require exclusive ownership, with no live
bytes exports or other readers.  This includes writes through
construction pointers obtained earlier.  All construction writes must
happen-before publication to another thread or buffer acquisition.

Previously exported storage may be reused once exclusive ownership
has been safely re-established under the API's existing rules.  In a
free-threaded build, a reference count of one alone does not establish
exclusive ownership.  Nor does that count grant permission to mutate
arbitrary bytes objects.

``PyBytesWriter`` already completes construction before returning the
object, so it is unaffected.


``memoryview``
~~~~~~~~~~~~~~

A stable memoryview's internal owner, the *managed buffer*, keeps the
underlying export alive and records whether its acquisition was stable.

Construction from a stable memoryview, slicing, casting,
``toreadonly()``, and C re-exports share this owner without repeating
the original exporter's conflict check.  The underlying export remains
active until every view and C export has finished using it.

When constructing a memoryview from another memoryview, ``access``
determines whether an ordinary acquisition is acceptable:

===========================  ====================  =======================
Underlying acquisition       ``access``            Result
===========================  ====================  =======================
Ordinary or stable           ``None``              Share existing owner
Stable                       ``"stable-read"``     Share stable owner
Ordinary or no acquisition   ``"stable-read"``     Plain ``BufferError``
===========================  ====================  =======================

An ordinary memoryview cannot be upgraded to a stable one, including
through ``PyObject_GetBuffer()``.  Making it read-only does not change
that rule.  An ordinary request from a stable memoryview returns a
read-only view if the requested representation is supported.  A
``PyBUF_WRITABLE`` request fails as it does today.

Slices and casts remain usable after their source view is released.
Here, ``tail`` keeps the stable export active:

.. code-block:: python

   view = stream.getbuffer(access="stable-read")
   tail = view[1:]
   view.release()
   stream.getbuffer()     # raises BufferConflictError

``memoryview.release()`` still raises plain ``BufferError`` while any
C export from that particular memoryview remains active.

For views that own an export, ``memoryview.obj`` continues to name the
object from which the export was acquired.  For ``BytesIO``, this is
the private exporter described below.

Creating dependent views or C re-exports, including released-state
checks and owner-count updates, must be synchronized with release.
The last release must not end the underlying export while another
thread registers access.  GC clearing must also defer release while
dependent views or C re-exports still need the export.


``io.BytesIO``
~~~~~~~~~~~~~~

``getbuffer(access=None)`` returns an ordinary writable view.
``getbuffer(access="stable-read")`` returns a read-only stable view.
All views of a stream participate in the same conflict checks:

========================  ================================  ========
Active access             New operation                     Result
========================  ================================  ========
Ordinary writable export  Ordinary acquisition              Succeeds
Ordinary writable export  Stable acquisition                Conflict
Stable export             Another stable acquisition        Succeeds
Stable export             Ordinary acquisition              Conflict
Either kind of export     Write, truncate, or reinitialize  Conflict
Either kind of export     Close                             Succeeds
========================  ================================  ========

Conflicts raise ``BufferConflictError``.  The methods affected are
``write()``, ``writelines()``, ``truncate()``, ``__init__()``, and
``__setstate__()``, as well as the conflicting acquisitions in the
table.  Reinitialization must check for conflicts before changing the
stream's contents, length, or position.  Existing mutation failures
with ordinary exports also change from plain ``BufferError`` to this
subclass.

Reads and cursor movement remain permitted.  Each export keeps the
backing bytes alive after close; a closed stream refuses new acquisitions.

``BytesIO`` does not use copy-on-write to bypass export conflicts.
Otherwise, its copy-on-write behavior is unchanged: a stable acquisition
may share bytes, while an ordinary writable acquisition must unshare
them when necessary.

The stream itself remains a non-exporter.  ``getbuffer()`` constructs a
memoryview over a private exporter whose name and layout are
implementation details.  Every acquisition from that exporter,
including one made through ``memoryview.obj``, uses those same
conflict checks.  Each export records its own kind of access.

Subclasses that inherit or explicitly invoke the base ``getbuffer()``
method retain these semantics.


Exporter Requirements
---------------------

An exporter that declares support takes responsibility for every
supported way to change the storage behind a stable view.  Immutable
storage needs no conflict tracking.  Mutable storage needs shared
checks that keep stable reads from overlapping with writes or other
conflicting access.

.. _Coordination Domains:

Sharing Storage and Detecting Conflicts
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

All aliases of the protected storage must share conflict checks and
state.  The storage covered by those checks is a *coordination domain*.

A domain can cover one allocation, one object, or a group of objects.
It may conservatively reject operations on disjoint regions to simplify
bookkeeping.

An ordinary request without ``PyBUF_WRITABLE`` does not require a
read-only result: the exporter may still return a writable view.  The
request is *known read-only* only when the exporter can establish, before
granting it, that the resulting access cannot write to protected storage.
Otherwise the request counts as *possibly writable*.  The exporter
must continue to make a consistent writability choice for ordinary
requests from all consumers.

For storage that needs coordination, stable and possibly writable
exports are active from the moment their records are added until their
release callbacks remove them.  Records must be added before
``bf_getbuffer`` returns success.  A write or storage change remains
active until it records completion;
longer-lived write access remains active until its observable release.
Adding and removing records must be atomic with respect to other
operations using the domain.  `Checking Every Access Path`_ covers
interfaces that do not report when write access ends.

While a stable export is active, the following rules apply:

===========================================  ===========
New operation                                Result
===========================================  ===========
Stable acquisition                           Compatible
Known read-only ordinary acquisition         Compatible
Possibly writable ordinary acquisition       Conflict
Write to protected memory or metadata        Conflict
Storage change that reaches the view         Conflict
Storage change that cannot reach the view    Compatible
Long-lived write-capable access              Conflict
===========================================  ===========

Conversely, a stable acquisition conflicts with active writes, write
access, or changes that could invalidate the protected storage.
An operation fails on conflict, but may wait to acquire the domain's
synchronization (`Accepting a Request`_).

Ordinary reads require no check for a stable-read conflict.
An exporter can switch to new private storage and modify it,
provided every existing view keeps its original storage valid and
unchanged.  Writes confined to that new storage need no checks against
the old domain.


.. _Exporter Audit:

Checking Every Access Path
~~~~~~~~~~~~~~~~~~~~~~~~~~

Before declaring support, the implementer must audit every supported
path to the protected storage and metadata, public or private, including:

* Python methods and C functions or macros that write, resize, close,
  replace storage, or return aliases and pointers;
* buffer acquisitions;
* other objects and exporter instances sharing the allocation;
* callbacks, reentrant calls, and code outside the exporter's control;
* shared-memory, I/O, and device writes during normal use; and
* GC clearing, finalization, and deallocation.

Every path that could conflict with a stable view must use the domain's
coordination and be able to fail or postpone its work without changing
or invalidating that view.  `Errors`_ also covers C interfaces and
cleanup that cannot raise an exception.  Calls which violate an
interface's documented rules are outside this audit.

The exporter must observe when raw write access is granted.  If it
can observe when access ends, it records that lifetime.  Otherwise,
before granting the pointer, it must atomically:

* reject the pointer request if a stable export is active; and
* otherwise, mark the domain permanently unable to grant stable reads.

Every alias must observe that permanent state.  Later stable requests
raise plain ``BufferError`` before checking for temporary conflicts,
even if callers have in fact stopped using the pointer.  A type which
allows writable pointers to escape without observing their acquisition
cannot declare support at all.


.. _Admission:

Accepting a Request
~~~~~~~~~~~~~~~~~~~

The exporter must check for conflicts and record an accepted operation
as one atomic action under the domain's synchronization.

Immutable stable exports and known read-only ordinary exports need no
conflict records.  Immutable exporters can omit ``bf_releasebuffer``
when there is no cleanup to perform.  Every coordinated stable or
possibly writable export requires that callback and sets ``view->obj``
to a new reference to the exporter itself.

Before ruling out conflicts, the exporter may inspect only information
that is safe to read while a conflicting operation is still active,
such as immutable support information or separately synchronized state.
It cannot inspect layout fields that the active operation may be
modifying without synchronization.  Merely taking the domain mutex
does not make those reads safe if that operation does its work outside
the mutex.

A coordinated stable or possibly writable acquisition proceeds as
follows:

1. Acquire the domain's synchronization.
2. Check support information that is safe to inspect at this point,
   and determine which access the request may grant.  Treat an ordinary
   request as possibly writable unless it is known read-only.
3. Reject the request if an incompatible operation is active.
4. Check the remaining representation and instance requirements while
   preventing operations that could change the state being inspected.
5. Add the export's record before releasing synchronization.
6. Fill the view, keeping any further synchronization needed to do so
   safely.  If acquisition fails, undo its work and remove the record
   before returning.  On success, leave the record for the release
   callback to remove.

Once recorded, a stable acquisition excludes writes and invalidation
while the exporter fills its view.  A possibly writable acquisition
excludes only stable acquisitions; the exporter's existing
synchronization must still protect its view construction from ordinary
operations.  Every successful view must satisfy the requested
representation.  Acquisition must not re-enter the exporter or make
an unfinished view available to other code.

Per-export state must survive shallow copies of the ``Py_buffer``
without depending on its address.  ``view->internal`` can refer to this
state; see `Keeping the Export Alive`_ for the consumer's obligations.


Writes and Calls That Can Release a Lock
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

A write or storage change can keep synchronization for the whole
operation.  Alternatively, it can add a record, release synchronization
while doing the work, and remove the record when finished.  An exporter
must not hold a domain lock for the lifetime of an export or wait for
another thread while holding it.

CPython critical sections need extra care: C API calls can suspend a
critical section and release its locks.  Callbacks can also give other
code a chance to re-enter the exporter.  If an operation relies on a
critical section alone, it must check conflicts after every callback
or possible suspension, and then finish the protected work without
another suspension or reentrant call.  Otherwise it needs an operation
record that excludes conflicts throughout the interval when its lock
might be released.  Holding a non-suspendable domain lock across
callbacks is not permitted.


.. _Release and Memory Ordering:

Ending an Export
~~~~~~~~~~~~~~~~

Before atomically removing an export's record, the release callback
must finish using protected bytes and metadata and complete cleanup
that could interfere with a subsequent operation.  It must remove the
record exactly once.  Harmless reference drops may follow removal.

The callback must neither change ``view->obj`` nor decrement its
reference; ``PyBuffer_Release()`` decrements it afterward.  The callback
must not set an exception or disturb an exception already being handled.

Both buffer callbacks run with an attached thread state.  Compatible
calls may run concurrently in a free-threaded build, so callbacks and
their bookkeeping must be thread-safe.  Cleanup, including GC clearing,
must preserve active protected storage.  The exporter retains the
owners of that storage for as long as necessary, and traverses
retained Python references according to the GC rules.


Making Completed Accesses Visible
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

When one incompatible operation finishes and another begins, the
first operation's accesses must *happen-before* the second's in the
C memory model.

An exporter using atomics must publish completion with release
semantics when a write or storage change finishes, or an export record
is removed.  The next incompatible operation must observe that
completion with acquire semantics before accessing the protected
storage.  Other synchronization mechanisms must provide equivalent
ordering.

No ordering is guaranteed between compatible operations or for
unrelated consumer memory (`Sharing Between Threads`_).


Declaring Support
-----------------

An exporter declares that its type's interfaces have been audited and
its buffer callback meets `Exporter Requirements`_.

The declaration applies only to that exact type.  A subclass needs its
own audit and declaration, even if it inherits the buffer callback.
Only the code responsible for initializing and auditing the type may
make the declaration.  It must finish configuring the type and make
the initial declaration before exposing the type for use or creating
instances or subclasses.

Both declaration paths below require:

* ``PyType_Ready()`` has completed successfully;
* the type and every base in its MRO have
  ``Py_TPFLAGS_IMMUTABLETYPE`` set;
* the metaclass is exactly ``type``; and
* the resolved ``bf_getbuffer`` is non-NULL and native, rather than
  the slot wrapper for a Python-defined ``__buffer__``.

Unmet type requirements raise ``TypeError``.  A capability mask other
than ``PyBUF_STABLE_READ`` raises ``ValueError``.


Choosing a Declaration Path
~~~~~~~~~~~~~~~~~~~~~~~~~~~

For a heap type that is immutable at creation, add this :pep:`820` slot
to its type specification:

.. code-block:: c

   PySlot_UINT64(Py_bf_buffer_capabilities, PyBUF_STABLE_READ)

The public slot carries a ``uint64_t`` value and can appear directly or
through ``Py_slot_subslots``, following :pep:`820`.  An invalid
declaration causes type creation to fail.

For a static type, or a heap type that needs further configuration
after creation, use this new Unstable C API function:

.. code-block:: c

   int PyUnstable_Type_RegisterBufferCapabilities(
       PyTypeObject *type, uint64_t capabilities);

``PyType_Ready()`` makes a static type immutable.  A heap type using
this path is created without the capability slot, configured, and then
made immutable with ``PyType_Freeze()``.  It then registers support
before making the type available for use.

The registration function returns ``0`` on success, or ``-1`` with an
exception set on failure.  A failed call leaves any existing declaration
unchanged.  With either path, CPython records the declaration only after
all checks and any required allocations have succeeded.

CPython's built-in exporters use equivalent internal initialization.


Keeping the Declaration Valid
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A declaration belongs to the type object, so every interpreter using
that type shares it.  Calling the registration function with the
already-declared mask returns ``0``, whether the original declaration
came from the slot or the function.  This allows repeated module
initialization and concurrent identical registrations.  Changing or
removing a declaration raises ``ValueError``.

CPython checks the type requirements listed above, but cannot verify
the audit or whether the type has already been used.  Registering
support cannot account for writable access granted earlier.  Declaring
support without meeting the requirements, or later replacing audited
interfaces through unchecked C-level mutation, is C API misuse.

CPython stores declarations in a process-wide internal table keyed by
exact type identity.  The table does not keep types alive.  When a heap
type is destroyed, its entry is removed before its memory can be reused.
Lookup, registration, and removal are synchronized, and no table lock
is held while calling an exporter.

There is no Python-level declaration API.  Python-defined :pep:`688`
buffer slots remain ineligible.


.. _Acquisition:

How CPython Handles a Request
-----------------------------

``PyObject_GetBuffer()`` and the Python-callable ``__buffer__`` wrappers
for C buffer slots perform the same checks for stable requests.  These
checks keep older exporters from silently ignoring the new flag.

For a stable request, CPython first zero-initializes the output
``Py_buffer``.  It then:

1. validates the complete numeric request, raising ``ValueError`` for
   an invalid combination;
2. checks that the object exports buffers, raising ``TypeError`` if
   it does not;
3. checks the exact type's declaration and, for a wrapper call, the
   callback being called.  An undeclared capability or a callback
   mismatch raises plain ``BufferError``; and
4. calls ``bf_getbuffer`` with the flags unchanged.

The exporter follows `Accepting a Request`_; CPython then checks its
returned fields before reporting success.


Returning a View or an Error
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

On success, the exporter must set ``view->obj`` to a new reference to
the exact object that was passed to the checked call, and set
``view->readonly`` to one.  CPython checks those two field values.
It relies on the exporter's audit and synchronization for the actual
stability guarantee.

If either field has the wrong value, CPython rejects the result with
``SystemError`` after cleaning it up.  It calls the original exporter's
``bf_releasebuffer``, if present, decrements the returned owner
reference if non-NULL, and clears the output structure.  It never
chooses a release callback from the unexpected owner.  This recovery
requires releasable export state and either a NULL owner or a valid
owned reference; it cannot repair arbitrary C API misuse.

A conforming failed acquisition leaves ``view->obj`` NULL and no
record, reference, or other resource for the consumer to release.


Calling Buffer Methods Directly
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A call such as
``obj.__buffer__(inspect.BufferFlags.STABLE_READ)`` goes through the
same checks, with ``PyBUF_SIMPLE`` as its base representation.

Calling a base class's ``__buffer__`` wrapper can select a different
C callback from the exact type's resolved ``bf_getbuffer``.  A stable
request through that wrapper succeeds only if the callbacks match;
otherwise it raises plain ``BufferError``.  Ordinary wrapper calls are
unchanged.

A direct C call to ``bf_getbuffer`` bypasses these checks and is not a
supported or portable way to request stability.  A Python-defined
``__buffer__`` cannot pass the checks for its own type, but it may
acquire and return a stable memoryview from a declared underlying
exporter.


Backwards Compatibility
=======================

The new flag, exception, and type slot are public CPython C API in
Python 3.16, initially unavailable under ``Py_LIMITED_API`` and outside
the Stable ABI.  Stable ABI inclusion awaits third-party experience;
a shim cannot supply the guarantee for arbitrary older exporters.

Existing buffer function signatures, the ``Py_buffer`` layout, and
``PyBUF_*`` values are unchanged.  Existing exporters declare no
capability unless explicitly opted in, and existing consumers do not
request it.  Ordinary requests retain their validation and dispatch
path after a test for ``PyBUF_STABLE_READ`` in the request flags.
``PyObject_CheckBuffer()`` still reports ordinary buffer
support and says nothing about stability.

Private consumer/exporter pairs that already pass the newly assigned,
previously undocumented bit will now encounter stable-request
validation.  An invalid combination raises ``ValueError``; an otherwise
valid request to an undeclared type raises plain ``BufferError``.

Opted-in exporters may newly reject ordinary acquisitions or mutations
while stable exports exist.  ``BytesIO`` also changes existing
live-export mutation failures to ``BufferConflictError``.
Catching the exception with ``except BufferError`` continues to work.

The bytes construction rule also applies to existing C extensions.
CPython cannot detect writes through retained pointers.  The bytes
C API documentation will state the ownership rule explicitly and
recommend ``PyBytesWriter``.

Opting in can change ``view->obj`` and release dispatch for ordinary
possibly writable exports that previously named an underlying owner.
Future migrations of exporters in CPython must assess these observable
changes under :pep:`387`.


Security Implications
=====================

CPython trusts the exporter's declaration.  If the exporter misses a
supported write path, a consumer relying on stable access can
encounter undefined behavior from a native data race.  Consumers
remain responsible for checking layout, bounds, alignment, and element
validity.


Performance
===========

Ordinary acquisition adds a predictable request-flag test.  Stable
acquisition adds request validation, a capability lookup, and output
initialization.  Mutable exporters add bookkeeping to writes, storage
changes, and possibly writable exports; ordinary reads need no record.
Shared domains may contend.  These are expectations, not measurements;
the implementation must benchmark both acquisition paths.


How to Teach This
=================

Teach read-only access and stable contents as separate guarantees,
using the alias and dependent-view examples.  Consumer documentation
covers acquisition, errors, and ownership; exporter documentation
explains the audit and admission rules.  Keep the runtime checks
explicitly separate from the exporter's synchronization responsibilities.


Implementation and Test Plan
============================

No implementation exists yet.  The prototype will need the acquisition
checks, both declaration APIs, exact ``bytes`` support, memoryview
propagation, and ``BytesIO`` coordination.  The slot generator and
public headers must keep the new names out of Limited API builds and
the Stable ABI.  ``_pyio.BytesIO.getbuffer()`` will accept ``access``
and report unsupported stable access with plain ``BufferError``.

Purpose-built static and heap test exporters will exercise both
declaration paths, heap-type configuration followed by freezing, work
outside domain locks, and coordinated pointer escape.  Out-of-tree
exporters will check that the public APIs suffice.

Tests on GIL-enabled and free-threaded builds must cover:

* flag and slot validation, registration errors without partial state
  changes, and rejection of unready or mutable types, mutable bases, custom
  metaclasses, and slots wrapping Python-defined ``__buffer__`` methods;
* non-inheritance of declarations, repeated registration after either
  declaration path and during module initialization, cleanup when a heap
  type is destroyed, and rejection of attempts to remove a declaration;
* stable reads concurrent with attempted writes under ThreadSanitizer;
* conflict detection while recorded operations modify layout outside
  domain synchronization;
* acquisition rollback and conflict checks concurrent with record removal;
* metadata lifetime after shallow copies, dependent views, C re-exports,
  synchronized handoffs, and GC cycles with differing clearing orders;
* coordinated pointer escape and subsequent permanent refusal;
* early failures, base-class buffer wrappers, and recoverable malformed
  postconditions; and
* CPython's bytes construction and copy-on-write paths preserving live
  exports, and ``BytesIO`` reinitialization failing without changing state.


Rationale and Deferred Work
===========================

Only exporters can coordinate all supported storage access paths.
Consumers cannot discover arbitrary locks or make aliases use them;
even an unsynchronized copy can race.  Exact-type declarations prevent
unaudited inheritance, and the gate prevents old exporters from
ignoring the new flag.  Failing on conflict avoids waiting on exports
whose owners may hold unrelated locks.

A separate ``PyObject_GetStableBuffer()`` would still need declaration,
gating, and coordination, while adding a parallel acquisition API for
wrappers and code generators.  A request flag uses their existing
interfaces.  The Python string parameter leaves room for additional
modes without making arbitrary C request combinations part of this
public interface.

A capability mask avoids consuming a type-flag bit for each mode.
The slot uses the established type-creation API; registration remains
Unstable while we gain experience with static and shared types.
Custom metaclasses are excluded initially to keep the declaration
model limited to ordinary type behavior.

Deferred work includes capability or export-mode introspection,
exclusive writes, safe wrapper delegation and memoryview upgrades,
C convenience or ownership-taking constructors, and more exporter
audits.  Combining future capability flags requires a later proposal.
